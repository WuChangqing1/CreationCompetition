# 01 多模型框架改造说明

## 为什么要改

原仓库虽然有 `models/__init__.py` 的动态发现函数，但训练和测试直接导入 `models.our.our_model.ourModel`。结果是新增模型即使文件名符合规则，也不会被 train/test 使用。

原调用链：

```text
train.py / test.py
        ↓ 直接 import
     ourModel
```

新调用链：

```text
train.py / test.py / run_model_cv.py
                ↓
    experiments/model_registry.py
          ┌─────┴─────┐
          ↓           ↓
       SVM/XGB      PyTorch
                      ↓
             models.create_model(opt)
                      ↓
       mlp/bilstm/lightweighttrans/lmf/mult/our/...
```

## 两层 Registry

`models/__init__.py` 只管理 PyTorch 完整模型。给定 `opt.model="mlp"`，它导入 `models/mlp_model.py` 并查找 `MLPModel(BaseModel)`。找不到模型会抛明确异常，不再 `exit(0)` 伪装成正常退出。

`experiments/model_registry.py` 是整体实验分派器。它先判断模型属于 Classical 还是 PyTorch：SVM/XGBoost 直接返回 sklearn/XGBoost estimator；其他模型必须继续走 `models.create_model()`。因此没有 train、CV、Registry 三套重复 if/else。

## 为什么 SVM/XGBoost 不走 BaseModel

BaseModel 的接口围绕 tensor、反向传播、optimizer 和 state_dict。SVM/XGBoost 的核心接口是 `fit/predict_proba`，强行继承会产生空 optimizer、假 forward 等误导代码。统一的是实验输入、fold、指标和结果，不是强行统一底层训练机制。

## 数据和公平比较

主架构比较固定 MFCC、DenseNet、personality enabled、seed 3407、同一组 subject folds。Classical 模型对 A/V 分别做时间均值后拼接 P；StandardScaler 位于 SVM Pipeline 内，只对训练 fold 调用 fit。

新 PyTorch adapter 统一输出 `emo_logits`、`emo_pred`、`emo_label`。新增深度模型默认使用 CrossEntropyLoss 且不加类别权重；OurModel 的 architecture-comparison 配置把辅助 Focal 权重设为 0。原 train.py 仍保留 config.json 的原 CE+Focal 行为，二者必须在报告中区分。

## Checkpoint 兼容

新 checkpoint 保存模型名、state_dict、最终配置、特征配置、fold 和 seed。test.py 的 `unpack_checkpoint` 同时接受旧纯 state_dict；旧格式需要通过 `--model` 告知模型名，默认仍是 our。

## 与目标结构的小幅差异

- DepMamba 当前只保留安全入口和网络包说明，没有伪造 mamba block/fusion/network；依赖缺失且适配未验证。
- confusion matrix 在 matplotlib 缺失时保存数值 CSV 并报告 SKIPPED，不伪造 PNG。
- 没有真实数据时不生成 fold 文件，也不写 raw_results。

这些差异都是为了遵守“可选项不能破坏 P0/P1”和“不伪造”的要求。
